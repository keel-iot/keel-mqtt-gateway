# v0.2.47 — Redis sidecar failover

Includes the shared-subscription corrections from
[v0.2.46](0.2.46.md) and fixes Redis failover when the gateway core remains
alive while its co-located Redis is unavailable.

## Fixed

- The Raft leader probes the designated Redis primary with authenticated
  `PING`, using a two-second deadline and no client retries. Connection
  refusal, timeout, and `LOADING` errors start the existing 30-second failure
  window even if the core remains present in gossip. Recovery resets it.
- After the failure window, unreachable Redis candidates are skipped and
  reachable candidates are considered in stable node-ID order. Only an
  acknowledged promotion is followed by a Raft designation update. A failed
  promotion leaves the designation unchanged for retry on a later tick.
- A recovered old primary is configured as a replica of the new primary.
  Observed loss of leadership stops promotion and topology updates.
- With `core.redis.password` configured, the chart now supplies `masterauth`
  as well as `requirepass`, allowing replicas to authenticate upstream.

## Compatibility and rollout

- Chart version, application version, and default gateway image are `0.2.47`.
- No Redis schema change, PVC reset, or data migration is required.
- Roll out cores one at a time while maintaining the Raft majority. All
  cores should be upgraded so any future Raft leader has the fixed detector.
  The existing edge Redis router supports the updated primary designation.
- Preserve the expanded Redis PVC capacity and monitor free space. This
  release does not change volume claim sizes or Redis image versions.
- The gateway does not automatically repair or delete malformed AOF files.
  The Redis persistence engine's handling of partial writes is outside this
  gateway fix. See the [incident and operations notes](../operations/redis-failover.md).

## Validation

- Go build, vet, and the default test suite.
- Race tests for membership, Redis routing, and server wiring.
- A Linux Docker integration test with two authenticated Redis 7.4
  instances: Redis-only failure with core membership unchanged, promotion,
  client redirection, replicated reads, new writes, and recovery of the old
  primary as a synchronized replica. Its Raft registry uses a single-voter
  test node with the topology count overridden; it does not validate
  multi-node elections or network partitions.
- Helm lint and template rendering with and without Redis authentication.

## Limits

Replication remains asynchronous. Stable candidate order does not rank
replication freshness or guarantee zero data loss. The topology has no
Redis write fencing that guarantees a single writable server throughout
every network partition. Disk exhaustion and the cause of the Redis
process restarts require operational mitigation independently of failover.
