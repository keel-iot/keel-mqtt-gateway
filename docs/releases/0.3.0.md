# v0.3.0 — Redis read optimizations and replication backlog configuration

Reduces Redis reads during offline-session inventory and MQTT delivery, and
exposes replication backlog sizing in the Helm chart. Includes the Redis
primary health checks and failover fixes from [v0.2.47](0.2.47.md).

## Changes

- Offline inventory skips clients already claimed by live connections before
  reading their Redis records, last-seen timestamps and subscriptions. It checks
  a fresh connection snapshot after the scan to exclude concurrent reconnects.
- Offline delivery selects clients whose exact ownership filters match the
  published topic from the local routing view before reading Redis. Shared
  group choices come from the same routing snapshot; live group members
  suppress offline shared delivery. Persisted subscriptions and QoS are still
  checked before enqueueing, and overlapping filters fetch each client once.
- Candidate subscription reads use bounded pipelines of up to 256 clients
  instead of one network round trip per client. Updates are read directly from
  Redis without introducing a subscription cache.
- QoS 0 publishes skip offline-store reads because they are never queued for
  offline delivery.
- `core.redis.replBacklogSize` sets the Redis replication backlog on every
  core, with or without authentication. The compatibility default remains
  `"1mb"`. Configure a larger value explicitly, for example:

  ```yaml
  core:
    redis:
      replBacklogSize: "128mb"
  ```

## Compatibility and rollout

- Chart version, application version and default gateway image are `0.3.0`.
- No Redis key-schema change, PVC reset or data migration is required.
- Upgrade cores while maintaining the Raft majority, and roll edges to apply
  the offline-delivery read optimizations. No coordinated shutdown is required.
- Preserve production resource settings and expanded PVC capacities in the
  deployment values. This release does not change their defaults, Redis image,
  persistence settings or quota accounting.
- Backlog sizing consumes additional RAM on every Redis instance. Size for the
  replication-stream rate and desired disconnect window with traffic and
  memory headroom. At a stream rate of 5 MiB/s, 128 MiB covers approximately
  25 seconds before traffic variation. Replication IDs and available offsets
  must also permit partial resynchronization.
- Redis replication remains asynchronous. This release does not guarantee
  lossless failover or automatically repair malformed AOF files.

## Validation

- Complete Go test suite, build and vet.
- Race tests for routing and offline delivery, including wildcards, overlapping
  subscriptions, shared selection with live members, ownership handoff,
  deduplication and persisted-subscription rechecks.
- Real Redis 7.4 tests: an inventory with 8,600 online clients skips their
  payload reads; client transitions, stale index entries and legacy unfiltered
  inventory remain supported. A 600-client subscription read uses batches of
  256, 256 and 88, observes subsequent updates, and rejects partial results
  after a Redis error.
- A local fully-online inventory benchmark decreased scan duration from about
  103 ms to 11.5 ms and Go allocations from 15.4 MB to 0.32 MB per pass. This
  measures the inventory operation, not production-wide CPU savings.
- Helm lint and template rendering with default backlog, explicit `128mb`,
  and Redis authentication enabled and disabled. Redis accepts the backlog
  setting as 134,217,728 bytes.
